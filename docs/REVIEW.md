# روتین review در گروه g07

## چرا review این‌قدر مهم است

1. **نمرهٔ فردی:** ۴۰٪ نمرهٔ فردی از «commit و review معنادار» در GitLab است. داور commentها و approveها را می‌بیند. کسی که فقط کد می‌زند و review نمی‌کند، نصف این بخش را از دست می‌دهد.
2. **دفاع:** ۲۰٪ نمرهٔ فردی توضیح دادن یک تصمیم **خارج از بخش خودت** است. سریع‌ترین راه یاد گرفتن بخش بقیه، review کردن MRهای آن‌هاست.
3. **جلوی باطل شدن یک بخش را می‌گیرد:** leakage، join غلط، تغییر قرارداد عمومی و secret در کد، هر کدام یک بخش کامل را صفر می‌کنند. یک جفت چشم دوم، ارزان‌ترین بیمه است.
4. **تداخل را زود پیدا می‌کند:** دو نفر که یک فایل را جدا عوض می‌کنند، فقط در review متوجه می‌شوند.

## روتین، قدم‌به‌قدم

### نویسنده (وقتی کار تمام شد)

1. تست‌ها را اجرا کن و push کن. صبر کن pipeline **سبز** شود.
2. توضیح MR را با قالب پیش‌فرض پر کن (`Closes #شماره`، چه عوض شد، چطور تست شد).
3. **Mark as ready** را بزن (از حالت Draft خارج شود).
4. در ستون سمت راست، **Reviewer** را انتخاب کن (جدول پایین).
5. در گروه بنویس: «MR !شماره آمادهٔ review است، reviewer: فلانی».

### reviewer (همان روز، حداکثر ۴ ساعت بعد)

1. MR را باز کن ← تب **Changes**.
2. اول توضیح MR را بخوان؛ بعد فایل‌ها را.
3. روی هر خطی که نظری داری comment بگذار:
   - موس روی شمارهٔ خط ← آیکون حباب ← متن ← **Start a review**
   - برای پیشنهاد تغییر مشخص، دکمهٔ **Insert suggestion** را بزن؛ نویسنده با یک کلیک قبولش می‌کند.
4. وقتی همهٔ commentها را گذاشتی ← بالای صفحه **Finish review** ← **Submit review**.
5. اگر مشکلی نیست یا بعد از اصلاح: دکمهٔ **Approve**.

### نویسنده (بعد از review)

1. به **هر** comment جواب بده: یا اصلاح کن و بنویس «اصلاح شد در commit فلان»، یا دلیلت را بنویس.
2. بعد از اصلاح، push کن. **Resolve thread** را فقط وقتی بزن که اصلاح شده یا توافق شده.
3. در گروه خبر بده: «!شماره اصلاح شد».

### merge (فقط حسن)

شرط: pipeline سبز + حداقل یک approve از غیر نویسنده + همهٔ threadها resolve شده.

## comment خوب چه شکلی است

سه قسمت: **چه دیدم، چرا مهم است، پیشنهادم چیست.**

| ضعیف | خوب |
|---|---|
| «این غلطه» | «اینجا items و payments با هم join شده‌اند؛ برای سفارشی با ۲ item و ۳ payment، مبلغ ۳ برابر می‌شود. پیشنهاد: هر کدام را جدا GROUP BY کن، بعد join.» |
| «LGTM» | «تأیید ✅ چک کردم: تست idempotency هست، خطای 409 درست برمی‌گردد، secret در log نیست.» |

حتی approve بدون ایراد هم یک comment کوتاه می‌خواهد که **چه چیزی را چک کردی**. این همان review معنادار است.

## چک‌لیست reviewer

- [ ] به تسک وصل است و همان کاری را می‌کند که تسک خواسته؟
- [ ] برای رفتار جدید تست هست؟ تست‌ها حالت خطا را هم امتحان می‌کنند؟
- [ ] secret، کلید، رمز یا دادهٔ خام در کد یا log نیست؟
- [ ] فایل‌های قرارداد عمومی دست نخورده‌اند؟
- [ ] هیچ چیز از `outcomes` (برچسب) وارد feature نشده؟ (leakage)
- [ ] زمان‌ها timezone دارند؟ تاریخ محلی با `America/Sao_Paulo`؟
- [ ] با کار بقیه تداخل ندارد؟ (همان فایل در MR دیگری عوض شده؟)
- [ ] اسم‌ها و ساختار با `docs/design/*.md` می‌خواند؟

## چه کسی review چه کسی را می‌کند

| نویسنده | reviewer اصلی | چرا |
|---|---|---|
| محمدرضا (داده) | احمد | feature مستقیم روی جدول‌های داده ساخته می‌شود |
| احمد (مدل) | محمدرضا | فیلترهای زمانی و برچسب به داده وابسته‌اند |
| آرمینا (سرویس) | احمد | API همان `build_features` و bundle مدل را استفاده می‌کند |
| حسن (انتشار) | آرمینا | probeها و تنظیمات اجرای API |

حسن همهٔ MRها را هم نگاه می‌کند، ولی جای reviewer اصلی را نمی‌گیرد.

## قاعدهٔ روزانه

- هر نفر **حداقل یک review در روز**.
- هیچ MRی بیشتر از یک روز منتظر review نمی‌ماند؛ اگر ماند، در گروه یادآوری کن.
- MR کوچک (زیر ~۳۰۰ خط) راحت‌تر و سریع‌تر review می‌شود.
